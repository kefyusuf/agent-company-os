# M5.4 — External Operation Boundary: OperationAttempt Ledger and Adapter Seam

**Status:** Design proposal — **not implemented**. Nothing here enables a real external effect.  
**Contract base:** M4.3 `ai-company-os.core@0.1.0-rc1` (FIX-10, FIX-11, INV-010/011, FLOW-04, `operation_attempt` canonical states, concurrency guarantees); M5.3-A/B/C as merged (PRs #6/#7/#9/#14–#17).  
**Master-spec anchor:** PR-C "runtime/tool adapter" — only after authorization gates are green (they are, at fixture level).

## Goal and non-goal

Introduce the **durable OperationAttempt ledger** and a **bounded adapter seam** so that a future real provider integration inherits safe semantics by construction, instead of being bolted on.

This stage does **NOT** connect any real LLM, tool, network or payment provider. All dispatches go through a **deterministic in-process fake adapter** whose outcomes are scripted by tests. `ExecuteExternalAction` remains a **NO-GO for production** until this whole stage is merged AND a real transport review happens.

## Why now, and what stays forbidden

M5.3-C made internal guards executable (budget reservation, one-time approvals, lineage). The next blockage for any real runtime is the **external outcome problem** (FIX-10): a dispatched action can return `unknown`, and no amount of internal bookkeeping turns unknown into success. The ledger, states and reconciliation rules must exist **before** the first real adapter — otherwise unknown is handled ad hoc at integration time, which is exactly the blind-retry hazard FLOW-04 forbids.

Still forbidden after this stage: real providers, credentials in code, network I/O, exactly-once claims, autonomous redispatch.

## Attempt state machine (canonical states only)

```text
planned -> authorized -> dispatched -> succeeded
                                    -> failed
                                    -> unknown -> reconciling -> resolved(succeeded | failed)
                                                              -> unresolved (terminal, human-gated)
```

- **planned → authorized:** the resolver re-enforces policy **at dispatch time** inside the command transaction (`PERMIT` is never a lease — M4.3 concurrency guarantee). Cost is reserved here (M5.3-C3 pool) and the *attempt* is what a consumed approval binds to (FIX-07/INV-010), not to success.
- **authorized → dispatched:** one `adapter.dispatch()` call. The adapter returns exactly one outcome: `succeeded`, `failed`, `unknown`. The attempt row, the outcome and the audit event commit atomically (INV-019).
- **unknown:** no state may be inferred. The attempt enters **reconciling** only via an explicit reconciliation command.
- **reconciling → resolved / unresolved:** the adapter's status query (fake in this stage) yields evidence; `resolved` records the outcome; `unresolved` is **terminal** and requires a recorded human decision before anything else may happen.
- **No redispatch from `unknown` (FIX-10).** Redispatch is possible only from `unresolved` *after* a recorded human reconciliation decision, and it always creates a **new** attempt with fresh authorization — never a mutation of the old row (attempt rows are append-only; immutable triggers).

## Adapter seam

```python
class ExternalAdapter(Protocol):
    def dispatch(self, attempt: DispatchRequest) -> DispatchOutcome: ...
    def status(self, attempt_ref: str) -> DispatchOutcome | None: ...
```

- `DispatchOutcome` is one of `succeeded`, `failed`, `unknown` plus an evidence reference (opaque string; never raw secrets).
- **`ScriptedExternalAdapter`** (test-only): outcomes come from a host-side script; this is the only adapter implemented in M5.4. Its existence proves the seam; it proves nothing about real providers.
- The adapter receives **no policy objects and no credentials** — only the attempt reference and an opaque, host-assembled payload fingerprint. Policy and identity stay in the gateway/resolver layer.

## Budget semantics across unknown (open question #1)

Company-level reservation happens at `authorized`. For `failed`, the reservation is refunded when reconciliation commits the failure. For `unknown`, the recommended semantics is **hold reserved until reconciliation settles** — releasing on unknown would let repeated unknowns strand unbounded spend. Recorded here as the owner's call.

## Reconciliation command (open questions #2–#3)

New gateway action `operation.reconcile` (trusted host, role-gated, audited):

- Input: attempt id + (optionally) adapter evidence.
- Reads the adapter status; transitions `unknown -> reconciling -> resolved(...)`; unknown-or-contradictory evidence records `unresolved` and stops.
- `unresolved` requires a **dedicated human reconciliation record** (new `operation_reconciliations` table: attempt id, decision `reissue`|`abandon`, human approver, policy version, expiry) — recommended over reusing `policy_approvals`, because approval semantics (exact payload/revision binding) do not map cleanly to "decide what an ambiguous external effect means".
- A `reissue` decision creates a new attempt: fresh `planned → authorized` evaluation, a **new** attempt id, and the old attempt stays `unresolved` forever (lineage preserved, INV-012 style).

## Pause interplay (FLOW-04)

- Company `paused`/`suspended`: **no new dispatches, no redispatches.** In-flight `unknown` attempts **may still be reconciled** (read-only status queries), because reconciliation resolves committed reality; it does not create new effects. This split is tested explicitly.

## Ordering and gates

| Step | Scope | Gate |
| --- | --- | --- |
| D-PR1 | Attempt ledger + state machine + `ScriptedExternalAdapter` seam; succeeded/failed paths with dispatch-time re-authorization, budget reservation and audit | Full suite green; ~15 new tests; verify floor raised |
| D-PR2 | `unknown` + reconciliation command + `unresolved` terminal + no-blind-redispatch guards | Scripted unknown→reconcile→resolve/unresolve flows; redispatch attempts from unknown denied |
| D-PR3 | Human reconciliation records + reissue-as-new-attempt + pause guards | Reissue requires record; paused company denies dispatch but allows reconciliation |

Every PR keeps the honest labels: **no real provider, no network, production NO-GO**.

## Open questions for review

1. **Budget on unknown:** hold reserved until reconciliation settles (recommended) vs release on unknown.
2. **Reconciliation authority:** trusted-host command, role-gated + audited (recommended) vs open to any reviewer appointment.
3. **Human decision record:** dedicated `operation_reconciliations` table (recommended) vs reusing `policy_approvals`.
4. **Adapter scope:** single generic seam + scripted test adapter only (recommended) vs pre-wiring any concrete provider stub.
