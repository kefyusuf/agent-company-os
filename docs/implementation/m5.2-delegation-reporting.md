# M5.2 — Deterministic Delegation & Reporting

**Status:** Implemented/tested **fixture-only** subset of M4.3 `ai-company-os.core@0.1.0-rc1`.  
**Dependency:** PR #2, itself stacked on the unmerged M4.3/M4.4 PR #1.  
**Safety:** No public API, authenticated principals, real LLM runs, finance transactions, network calls or third-party operations.

## Purpose

Demonstrate that a persistent organizational hierarchy can delegate a single task down, accept bounded work, preserve immutable report versions, and roll sources up without misrepresenting a report review as task acceptance.

The fixture contains **five distinct identities**: CEO → CTO → Engineering Manager → Backend Engineer → Research Subagent. The research identity is marked `temporary`, but **temporary creation, lifetime management, actual model execution, and cleanup have not been implemented**.

## Implemented

- `Workflows(Store)` uses the existing SQLite connection, transactional command receipts, tenant-scoped IDs, and append-only audit events.
- `OfferDelegation` checks **current** parent accountability, active company, target's **direct manager** position, task state, revision and a configurable depth bound (fixture default: 4).
- `AcceptDelegation` requires the exact target appointment, a still-active parent/delegator and unchanged reporting relationship; child Task is created only on acceptance, atomically with acceptance and audit records.
- `Store.create_task(parent_id=...)` now rejects creating a child Task directly even when the parent exists: the explicit delegation path is mandatory.
- `StartTask` and `ResumeTask` enforce `assigned → in_progress` and `changes_requested → in_progress` respectively.
- `AddEvidence` stores *provided* source references and SHA-256 digests. This **does not verify** the external artifact or the truth of a claim.
- `SubmitReport` produces immutable report version, evidence and/or accepted direct-child report references, and transitions `in_progress → submitted`.
- `BeginReview` binds a specific report/version to an authorized parent-task reviewer and transitions `submitted → under_review`.
- `ReviewReport` records an immutable `Review` decision for exactly the previously selected version. `accepted` leaves Task `under_review`; `changes_requested` returns Task to `changes_requested`.
- `AcceptTask` is a **limited fixture-only** acceptance guard: requires authorized parent reviewer, accepted report, all child Tasks accepted, no pending offered delegations, and every accepted child linked through the accepted parent report.
- Same persistent agent may fill multiple positions for delegation; the same identity cannot satisfy the **independent** review gate across appointments.
- Report content, reviews, evidence, and report/evidence reference relationships use SQLite immutability triggers.
- Scoped `report_sources` gives only the report author or authorized parent-task reviewer immediate source IDs.

## Contract-compatible example

```text
CEO creates/starts ROOT
CEO --Offer/Accept--> CTO-TASK
CTO --Offer/Accept--> MANAGER-TASK
Engineering Manager --Offer/Accept--> BACKEND-TASK
Backend Engineer --Offer/Accept--> RESEARCH-TASK

Research: EvidenceRef -> Report v1
Backend: BeginReview -> Review(accepted) -> AcceptTask(RESEARCH)
Backend: Report referencing Research + own EvidenceRef
Manager: BeginReview -> Review(accepted) -> AcceptTask(BACKEND)
Manager: Report referencing Backend
CTO: BeginReview -> Review(accepted) -> AcceptTask(MANAGER)
CTO: Report referencing Manager
CEO: BeginReview -> Review(accepted) -> AcceptTask(CTO)
CEO: Report referencing CTO
ROOT remains SUBMITTED: human Owner delivery/approval is NOT implemented
```

The end-to-end test verifies **record consistency** and references, **not** LLM reasoning, external factual verification, software quality, or business acceptance criteria.

## Safety caveats — explicitly NOT solved

1. **Identity authentication:** `Actor` is caller-supplied, not cryptographically authenticated. Never expose these methods directly to users or untrusted tools.
2. **Full policy engine:** Budgets, approval fingerprints, organization-level policy override rules and capability checks remain unimplemented; the fixture is not a deployable governance layer.
3. **Activation:** The test fixture changes the company to `active` directly in SQLite to simulate work. **This bypasses real readiness/Finance coverage** only in isolated tests; it is not an activation implementation.
4. **Independent reviewer types:** Only independent review is represented. Combined-role management review without independence must be modeled explicitly before relaxing the guard.
5. **Task acceptance criteria:** The fixture has no independently validated domain-specific acceptance criteria, QA attestation, waivers, or owner approvals. `AcceptTask` is not production-safe.
6. **Delegation lifecycle:** Decline, revoke, TTLs, budgets and policy-scoped subagent capabilities are not implemented.
7. **Information security:** Report read scope is deliberately narrow; full tenant/project ACL and secure logging/retention are not implemented.
8. **Memory/runtime/recovery:** No genuine AgentRun, checkpoint, source verification, business memory promotion, external OperationAttempt or reconciliation.
9. **Report delivery:** CEO's root report is `submitted`, not human-accepted/closed. Do not present it as a completed company task.

## Tests exercised

The new cases cover complete five-level rollup, parent/child responsibility, direct-report authorization, target acceptance, stale revisions, idempotency, cross-tenant denial, pause denial, revoked delegator, depth limit, report source ownership, immutable report/review content, revision after requested changes, exact report-version review binding, same-identity self-review denial, pending/unfinished children blocking acceptance, rejected undelegated child creation, and reopen/retrieve persistence.
