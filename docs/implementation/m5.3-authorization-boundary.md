# M5.3 — Trusted Command Boundary & Authorization Gates

**Status:** Reviewed implementation specification proposal; **not implemented**.  
**Contract base:** M4.3 `ai-company-os.core@0.1.0-rc1`, M5.1/M5.2 local fixture.  
**Primary risk:** `Actor` is currently supplied by callers and can be forged. Direct Store/Workflows access must never be exposed to untrusted model or network input.

## Goal and non-goal

Introduce an **authenticated and authoritatively scoped command boundary** before attaching any LLM/runtime, user-facing API, external tool, customer data, or high-impact external action.

This stage does **not** introduce a cloud identity provider, production deployment, new UI, full company compiler, OAuth service, microservices, agents-as-accounts or an external tool sandbox.

### Trust boundary

```text
Untrusted: user text, LLM output, tool-returned text, retrieved memory
                    |
             command proposal
                    v
 Trusted command gateway
   - trusted transport verifies real principal
   - resolves current company / active appointment / task from store
   - checks policy, capability, company state, delegation and action scope
   - checks revision, budget, and approval guards
   - applies command and audit in one transaction
                    |
              canonical Store
```

**No `Actor` is accepted as authority solely because an LLM submitted an ID or a role string.** The boundary resolves actor identity and appointments from an authenticated principal controlled by the host.

## Minimal command envelope

Proposed logical fields:

```yaml
command:
  command_id: CMD-0001
  type: task.start
  schema_version: 1
  principal_ref: trusted-transport-only
  company_id: COMPANY-DEMO-001
  target_ref: TASK-100
  expected_revision: 3
  idempotency_key: task-100-start-3
  payload: {}
```

**Security rule:** `principal_ref` is not a bearer credential or identity proof merely because it appears in serialized command data. Only the boundary derives/attests it from its trusted runtime/transport. Never include raw API keys or access tokens in audit logs or LLM prompts.

## Minimum authorization decision

`authorize(action, principal, appointment, task, resource, policy, company_state)` returns one of `PERMIT`, `DENY`, `APPROVAL_REQUIRED` and a durable decision reference.

Default `DENY` on missing fields, unrecognized action, invalid/expired principal, inactive appointment, foreign company/task/resource, stale delegation, suspended/paused company operational work, missing required capabilities, budget violation, absent independent verification or required human approval.

**Important:** Distinguish request-time lookup and execution-time revalidation; a prior `PERMIT` does not authorize later external action without checking current state.

### Required invariants for first code PR

| ID | Guard | Expected rejection |
| --- | --- | --- |
| M5.3-A01 | Actor must be derived from trusted authentication | Forged ID/appointment |
| M5.3-A02 | Active appointment belongs to principal and company | Cross-company or ended appointment |
| M5.3-A03 | Action explicitly allowed for task + appointment | Missing task scope |
| M5.3-A04 | Deny unknown operation by default | Unknown command/permission |
| M5.3-A05 | Only authorized position chain may delegate | Peer, foreign manager, unaccepted offer |
| M5.3-A06 | Reviewer independence checks underlying identity | Same-agent second appointment |
| M5.3-A07 | Command state revision checked | Stale expected revision |
| M5.3-A08 | Idempotency key scoped to tenant, actor/action, digest | Duplicate side effect or conflicting key |
| M5.3-A09 | Company state enforced at execution | Pause/suspend blocks new work |
| M5.3-A10 | Internal state change and audit record atomic | Mutation without auditable event |
| M5.3-A11 | Explicit human approval binds exact action/payload/revision | Approval reused or widened |
| M5.3-A12 | Tool caller cannot write policy/credentials through text or memory | Prompt injection attempted privilege escalation |

Owner-human operations use an authenticated human principal. Human and agent actors are not interchangeable, and a real human is not faked through `AgentIdentity`.

## Service/API contract constraints

1. **Single ingress:** expose only a trusted gateway/controller, not `Store`, raw SQLite connection, or `Workflows` to untrusted callers.
2. **Trusted identity source:** associate the host-authenticated human/service/agent execution with immutable principal metadata and attested active appointment; reject caller-supplied authority.
3. **Policy evaluation in the same protected transaction** for internal commands. Where the service action crosses the transaction boundary, reauthorize and record `OperationAttempt`.
4. **No privilege unions across appointments**. Each operation selects exactly one active appointment and scoped task/delegation.
5. **Protected audit:** command outcome, policy version, decision, affected record revision and causation/correlation references. No secret values.
6. **Explicit result types:** permitted/denied/approval_required, rejection reason, retryability and whether state changed. Never treat LLM prose as evidence of success.

## First implementation increments

### PR-A: Local authorization gateway and negative tests

Implement small, testable command boundary over the *existing* SQLite Store; add a **trusted test principal fixture** and verify it cannot impersonate another agent or company. Do not claim production authentication merely because the fixture accepts a token or special class.

Maintain full compatibility with the existing 46 deterministic tests. Add focused tests for deny-by-default, stale appointment, cross-company access, role switching, unauthorized direct child creation, and atomic rejection with zero state mutation.

### PR-B: Policy and acceptance guards

Formalize role+appointment+task-scoped action matrix; implement required acceptance criteria, independent review and audited human approval matching on exact resource/revision. No LLM integration.

### PR-C: Runtime/tool adapter

Only after previous gates are green, introduce a bounded provider adapter with no unreviewed high-impact tool. Real external effects remain disabled until `OperationAttempt` reconciliation and applicable approval controls are tested.

## Release / go-no-go

| Evidence | For local fixture | For external side effects |
| --- | --- | --- |
| Reproducible deterministic tests | Required | Required |
| Verified caller principal | Fixture proof adequate for testing | Actual host authentication required |
| Task, company, appointment and resource policy | Negative cases mandatory | Full policy enforcement mandatory |
| Evidence verification and acceptance criteria | Known limitations disclosed | Applicable criteria verified |
| External idempotency, approval and reconciliation | May remain disabled | Mandatory |
| Audit and revocation propagation | Durable local logs | Guaranteed at execution boundary |

**NO-GO** on a production LLM-tool system while the current caller-asserted `Actor` path or raw database access remains reachable from untrusted inputs.
