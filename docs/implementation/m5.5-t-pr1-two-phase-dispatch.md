# M5.5 T-PR1 — Two-Phase Dispatch and the Recovery Command (design)

**Status:** Design drafted and **decisions approved by the owner (2026-11-21)**; implementation not started. Nothing here enables a real external effect.  
**Base:** [M5.5 real transport review](m5.5-transport-review.md) — owner-approved decisions #1–#6 (2026-11-20); M5.4 external operation boundary (PRs #20/#23/#27).

## Goal and non-goal

Change the dispatch code shape from **one atomic transaction** (planned→authorized→dispatched→outcome, INV-019) to **commit-then-dispatch** (G-T1), and define the **recovery command** that resolves attempts resting mid-flight (G-T2) — so that the first real transport inherits the safe shape instead of retrofitting it. Still NO real provider, NO network: the only adapter remains `ScriptedExternalAdapter`, extended to simulate crash windows deterministically.

## Two-phase dispatch shape

**Phase 1 — authorization commit (inside the command transaction):**
gateway policy enforcement (fresh `planned → authorized` evaluation, unchanged), attempt insert, **transport identity recorded before any external call** (owner-approved T-PR1 candidate: the attempt id doubles as the provider idempotency-key material — G-T4), budget reservation, receipt. Then COMMIT.

**Phase 2 — effect + settlement (a separate short transaction, after the commit):**
`adapter.dispatch()` call → `authorized → dispatched → outcome` transitions, `adapter_ref`/evidence recording, budget settle (refund on `failed`; consume on `succeeded`; hold on `unknown`).

At fixture level phase 2 runs **synchronously right after phase 1 inside the same gateway call** — the observable UX of `operation.dispatch` is unchanged; only the transaction boundary moves. A real transport later swaps the phase-2 executor; the ledger semantics do not change again.

## Crash windows the recovery command must resolve

| Window | Ledger state | External reality | Resolution |
| --- | --- | --- | --- |
| After phase-1 commit, before call | `authorized` + transport id | Untouched | See decision Q1 below |
| During the call | `authorized` + transport id | **Possibly touched** | Ambiguous by construction |
| After call, before phase-2 commit | `authorized`/`dispatched` + transport id | Effect likely landed; provider may know the outcome | Adapter status is the only evidence |

The transport identity is recorded **pre-call** precisely so that a post-crash status query is possible without knowing whether the call completed (T1 direction in the M5.5 threat model).

## Recovery command (owner decision #1, M5.5)

New trusted-host gateway action **`operation.recover`** — role-gated (company-scoped grant, same discipline as `operation.reconcile`), audited, receipted/idempotent, **command-driven only** (no background supervisor, per the owner decision):

- Valid from: attempts resting at `authorized` or `dispatched` without a settled outcome (the two mid-flight rest states the two-phase shape introduces).
- Evidence: **adapter status via the transport id is the only evidence** — never internal bookkeeping.
- Settled evidence → missing transitions applied (`→ dispatched → outcome`) and budget settled; audit records `operation.recovered`.
- No/ambiguous evidence → the attempt enters the **existing human-gated ambiguity path**: `→ unknown`, then `operation.reconcile`/`operation.decide` proceed unchanged (decision Q1 below ratifies this mapping).
- **Recovery never re-dispatches** (owner decision #2: dispatch retries forbidden at every layer). The only redispatch paths remain D-PR3 reissue or a fresh attempt.

## State-machine extension

Current `ATTEMPT_TRANSITIONS` gain exactly two entries so mid-flight rest states can enter the ambiguity path:

```text
('authorized', 'unknown')    # recovery: no settled provider evidence
('dispatched', 'unknown')    # recovery: effect sent, outcome unrecorded
```

`unknown` → `reconciling` → resolved/unresolved is unchanged; terminal `unresolved` and the FIX-10 guard semantics (D-PR3) are unchanged. No transition leaves `succeeded`/`failed`/`unresolved`; no automatic transition exists anywhere.

## Adapter seam change (fixture-only)

`ScriptedExternalAdapter` gains a deterministic crash-window simulation: a scripted pseudo-outcome (e.g. `'crash'`) makes `dispatch()` **record the send in adapter history** (so a later `status()` query returns real evidence) and then raise, aborting phase 2 — modeling "process died after the provider received the call, before the ledger learned". No network, no real effects; it only makes G-T2 contract-testable now.

## Budget semantics

Unchanged and explicitly re-stated: reserve at authorization (phase 1), refund on settled `failed`, consume on `succeeded`, **hold on `unknown`**, hold on terminal `unresolved` (owner decision #1, M5.4). Recovery-induced `unknown` keeps the hold; the human path settles it.

## Decisions (approved by the owner, 2026-11-21)

1. **`authorized`/`dispatched` with no settled provider evidence (Q1):** map to **`unknown`** and reuse the existing human-gated reconcile/decide machinery. Owner approved over a new terminal state; one ambiguity path, one budget rule, one human gate.
2. **Phase-2 execution model at fixture level (Q2):** **synchronous post-commit** inside the same gateway call. Owner approved over a two-command flow now; the ledger shape is what matters and the command UX stays stable. A real transport later swaps only the phase-2 executor.
3. **Recovery command form (Q3):** **`operation.recover`** — role-gated with a company-scoped grant (reconcile discipline), receipted/idempotent, audited, command-driven only. Owner approved over folding recovery into `operation.reconcile` (which keeps its `unknown`-only rule intact).
4. **Transport identity at authorization time (Q4):** the attempt id is recorded as idempotency-key material in **phase 1, before any call**. Owner approved; this is what makes post-crash status queries possible (G-T4). Provider-side mapping completes in T-PR2.

## What stays NO-GO

Real providers, network I/O, credentials in code or fixtures, exactly-once claims, autonomous redispatch, unattended background recovery, payments, customer-data export and production deployment remain forbidden until the M5.5 gates have recorded evidence and the owner records an explicit GO.
