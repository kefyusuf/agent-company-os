# M5.3-B2 — SQLite Policy Resolution at the Command Boundary

**Status:** Draft implementation targeting `main`. [PR #7](https://github.com/kefyusuf/agent-company-os/pull/7) has merged after independent exact-source 49/49 unit tests.  
**Dependency:** M5.3-A fixture gateway + M5.3-B1 pure PolicyEvaluator.  
**Safety:** **NO-GO** for real LLM tool execution, production systems, payments or deployments.

## Purpose

Close the gap between a policy evaluator that checks caller-constructed Python values and the current SQLite-backed command workflow. **All policy facts are now resolved from canonical SQLite records by a trusted in-process adapter**, inside the same local write transaction that will perform the domain command.

This is still **test-host-only**. Direct SQLite, Store, Workflows and FixtureSessionHost access bypass the boundary. It does **not** establish genuine authentication.

## What this PR adds

- `company_os/policy_store.py`: `SQLitePolicyResolver`, versioned company policy/rules, company-specific appointment capabilities, exact grants, limited budget snapshots and example approval records.
- `PolicyCommandGateway`: explicit, resolver-required gateway class. It evaluates an action before calling the existing Store/Workflows command in the **same SQLite transaction**.
- The older `CommandGateway(store, fixture_host)` remains functional **only for legacy M5.3-A local tests**, without any claim of policy enforcement. Never expose it to untrusted inputs.
- Strict **default deny** when no active policy, no action rule, unrecognized task/resource, missing scoped grant, changed role/capability/company/task state or expired appointment/grant.
- A single `ScopeGrant` binds **one company + one appointment + one task + one action + one derived resource**. No union of an agent's different appointments.
- A task's resource is derived from **trusted SQLite task IDs**, not from a model-supplied resource string. New root tasks use a company-scoped resource.
- Reporter/reviewer actions resolve the report's source Task; accepted delegation resolves its parent Task.
- Task expected revisions are compared to current records before policy evaluation. For `delegation.accept`, the expected revision belongs to the **delegation offer**, not the parent Task.
- A permitted command records the policy version, action and derived resource in the same transaction as its business mutation. If a later domain guard fails, the permit event rolls back. The gateway records a **minimal** denial audit event separately (action+error code, never raw payload).
- Stored rules must explicitly enumerate allowed task states; malformed stored policy JSON and malformed booleans fail closed.
- If independent-review provenance is incomplete, **different agents alone are not sufficient evidence of independence**. Rules requiring verified independence are blocked until trusted contributor/delegation lineage is available.

## Explicitly disabled until subsequent work

**Approved does not mean executed.** The pure policy engine can evaluate a matching human approval snapshot, but this integration still refuses to execute **all approval-required actions** because atomic one-time consumption is not implemented. `AUTH_APPROVAL_CONSUMPTION_NOT_IMPLEMENTED` is deliberate.

**Budget checks do not debit funds.** Actions with nonzero fixed costs are blocked (`BUDGET_RESERVATION_NOT_IMPLEMENTED`) until transactionally reserved and audited.

**No fully independent verification yet.** Existing managerial report review works under current fixture Workflows guards when no separate independent-verification policy is demanded. For a policy requiring actual independent review, the resolver fails closed until verified provenance and reviewer lineage exist.

### Persisted tables

| Table | Meaning |
| --- | --- |
| `company_policy_versions` | One active version per company |
| `company_policy_rules` | Per-action role/capability/state requirements |
| `appointment_capabilities` | Trusted assessed capability snapshot for one appointment |
| `policy_grants` | Explicit action/resource/task/appointment authority with expiry |
| `policy_grant_versions` | Each grant is bound to the active policy version at issuance; stale grants do not auto-carry into new policies |
| `policy_budgets` | Remaining budget snapshot (not an accounting ledger) |
| `policy_approvals` | Demonstration approval intent fingerprints (not real Owner-authenticated approval) |

**Provisioning limitation:** These records are populated directly by a trusted test fixture. No Owner-authenticated policy editor, append-only policy publication, immutable policy migration, capability attestation or administrator API is implemented. Do not treat DB rows as independently trustworthy if an untrusted process has database access.

## M5.3-B2 replay hardening — 2026-11-08

[Issue #10](https://github.com/kefyusuf/agent-company-os/issues/10) now has a **proposed code-level fix** in this branch:

- `policy_gateway_receipts` stores a **successful** command's identity/appointment, idempotency key, canonical request digest, immutable result, original pre-action Task state, accountability, resource and policy-version/rule fingerprint. Storage occurs in the **same SQLite transaction** as the domain mutation and audit.
- On an **exact** repeat, the gateway looks up the receipt **before current task-state/revision guards**, but **after** trusted session resolution, envelope validation, active appointment, company-state and CEO root-task restrictions.
- The resolver rechecks the **current** company, agent appointment, role, assessed capability, exact scoped grant/expiry, budget policy, policy version, policy rule digest, resource and unchanged task accountability. The recorded original Task state is used **only** to validate the originally committed action; it is not read from user/model payload.
- If the current policy, grant, appointment, company or resource conditions fail, even an existing receipt is **denied**.
- If the same key is reused with different payload/actor/appointment, return `IDEMPOTENCY_CONFLICT`. A successful exact repeat returns the previous result **without redispatching** the domain action. The gateway writes a distinct minimal replay-authorized audit event.
- `report.sources` is read-only and does not create a persistent gateway command receipt. High-risk approval/cost actions are still **disabled**.

**Regression cases added** in `tests/test_policy_gateway.py` include task transition, start, delegated accept, conflicting payload, ended appointment, revoked/expired grant, paused company, different policy version, in-place rule change, task-accountability transfer and persistence across SQLite restart.

**Verification boundary:** After these source changes, a separate SQLite-only DDL/insert/uniqueness smoke test **passed**. **The new Python regression cases were committed but have NOT been run on a full GitHub checkout**, because the private GitHub repository cannot be fetched into this isolated container session. The earlier **101/101 partial-harness test result predates these changes** and must not be presented as evidence for the replay fix.

**Known remaining caveat:** This is still a trusted-fixture, in-process prototype. Receipts are NOT permanent access tokens, but real principal authentication, actual human approvals, budget reservation, independent evidence, safe external-operation retries and a complete CI/full-checkout test run are outstanding.

## Additional replay hardening and offline verification (2026-11-08)

The replay reauthorization branch now additionally checks the **live accepted delegation**, the child Task's parent/accountability, the current delegator appointment and the direct reporting relationship. An offer subsequently revoked, removed child, transferred child accountability or changed hierarchy **cannot** be used to retrieve a cached successful delegation-accept response. Replay also checks that the assigned appointment of an existing Task still matches the original assignment. These guards are present in source with new regression cases, but **the full repository Python tests have not yet been executed**.

A standalone, standard-library verifier has been added at `scripts/verify.py`. From the repository checkout:

```sh
python3 scripts/verify.py --output .local/verification.json
```

The command discovers and runs **all `tests/` unittest cases**, compiles `company_os/` and `tests/`, and records time, checked-out Git SHA, working branch, Python version, discovered test count, results and failure diagnostics in a local JSON file. It refuses to report success for zero discovered tests and requires no CI minutes, network or credentials. `.local/` is gitignored.

**Verifier smoke-test evidence:** The helper was executed in an isolated one-test demonstration checkout and produced `tests: PASS (1 discovered)`, `syntax: PASS`, and a JSON document with `all_passed=true`. This smoke test **does not validate any agent-company-os functional test** and cannot be represented as complete checkout success.

## Policy-gateway provenance safeguard (2026-11-08)

The new `PolicyCommandGateway` refuses to adopt a `command_receipts` entry previously produced by the legacy fixture `CommandGateway` when **no corresponding policy gateway receipt** exists. The old receipt contains an idempotent domain result but **does not attest a checked policy version, resource grant or task scope**. Returning it as a newly policy-authorized result would be retrospective authorization laundering.

A negative regression test `test_legacy_receipt_cannot_be_adopted_by_policy_gateway` was added to `tests/test_policy_gateway.py` and the deny code is `AUTH_UNATTESTED_LEGACY_RECEIPT`. This test **has not yet been run together with the full repository suite**; it is an implementation candidate, not a passing security proof. Legacy `CommandGateway` remains fixture-only and must not be exposed.
