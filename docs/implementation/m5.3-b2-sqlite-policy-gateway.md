# M5.3-B2 — SQLite Policy Resolution at the Command Boundary

**Status:** Draft implementation, stacked on [PR #7](https://github.com/kefyusuf/agent-company-os/pull/7).  
**Dependency:** M5.3-A fixture gateway + M5.3-B1 pure PolicyEvaluator.  
**Safety:** **NO-GO** for real LLM tool execution, production systems, payments or deployments.

## Purpose

Close the gap between a policy evaluator that checks caller-constructed Python values and the current SQLite-backed command workflow. **All policy facts are now resolved from canonical SQLite records by a trusted in-process adapter**, inside the same local write transaction that will perform the domain command.

This is still **test-host-only**. Direct SQLite, Store, Workflows and FixtureSessionHost access bypass the boundary. It does **not** establish genuine authentication.

## What this PR adds

- `company_os/policy_store.py`: `SQLitePolicyResolver`, versioned company policy/rules, company-specific appointment capabilities, exact grants, limited budget snapshots and example approval records.
- `PolicyCommandGateway`: explicit, resolver-required gateway class. It evaluates an action before calling the existing Store/Workflows command in the **same SQLite transaction**.
- The older `CommandGateway(store, fixture_host)` remains functional **only for legacy M5.3-A local tests**, without any claim of policy enforcement. Never expose it to untrusted inputs.
- Strict **default deny** when no active policy, no action rule, unrecognized task/resource, missing scoped grant, changed role/capability/company/task state or expired appointment/grant.
- A single `ScopeGrant` binds **one company + one appointment + one task + one action + one derived resource**. No union of an agent's different appointments.
- A task's resource is derived from **trusted SQLite task IDs**, not from a model-supplied resource string. New root tasks use a company-scoped resource.
- Reporter/reviewer actions resolve the report's source Task; accepted delegation resolves its parent Task.
- Task expected revisions are compared to current records before policy evaluation. For `delegation.accept`, the expected revision belongs to the **delegation offer**, not the parent Task.
- A permitted command records the policy version, action and derived resource in the same transaction as its business mutation. If a later domain guard fails, the permit event rolls back. The gateway records a **minimal** denial audit event separately (action+error code, never raw payload).
- Stored rules must explicitly enumerate allowed task states; malformed stored policy JSON and malformed booleans fail closed.
- If independent-review provenance is incomplete, **different agents alone are not sufficient evidence of independence**. Rules requiring verified independence are blocked until trusted contributor/delegation lineage is available.

## Explicitly disabled until subsequent work

**Approved does not mean executed.** The pure policy engine can evaluate a matching human approval snapshot, but this integration still refuses to execute **all approval-required actions** because atomic one-time consumption is not implemented. `AUTH_APPROVAL_CONSUMPTION_NOT_IMPLEMENTED` is deliberate.

**Budget checks do not debit funds.** Actions with nonzero fixed costs are blocked (`BUDGET_RESERVATION_NOT_IMPLEMENTED`) until transactionally reserved and audited.

**No fully independent verification yet.** Existing managerial report review works under current fixture Workflows guards when no separate independent-verification policy is demanded. For a policy requiring actual independent review, the resolver fails closed until verified provenance and reviewer lineage exist.

### Persisted tables

| Table | Meaning |
| --- | --- |
| `company_policy_versions` | One active version per company |
| `company_policy_rules` | Per-action role/capability/state requirements |
| `appointment_capabilities` | Trusted assessed capability snapshot for one appointment |
| `policy_grants` | Explicit action/resource/task/appointment authority with expiry |
| `policy_budgets` | Remaining budget snapshot (not an accounting ledger) |
| `policy_approvals` | Demonstration approval intent fingerprints (not real Owner-authenticated approval) |

**Provisioning limitation:** These records are populated directly by a trusted test fixture. No Owner-authenticated policy editor, append-only policy publication, immutable policy migration, capability attestation or administrator API is implemented. Do not treat DB rows as independently trustworthy if an untrusted process has database access.
