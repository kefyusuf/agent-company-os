# M5.3-A — Trusted Fixture Command Gateway (Local Proof)

**Status:** Implemented as an **in-process fixture-only guard**, proposed in this PR.  
**Source:** [Issue #5](https://github.com/kefyusuf/agent-company-os/issues/5)  
**Architecture baseline:** `ai-company-os.core@0.1.0-rc1`  
**Not production authentication, not full policy engine, not a network API.**

## What changed

- `company_os/gateway.py` adds a strict allowlisted `CommandGateway`.
- `FixtureSessionHost` issues **opaque Python session objects** to the **trusted test harness**, never via serialized agent/user prompts. The gateway resolves `company_id` and `agent_id` from that host session, not from a submitted `Actor`.
- The untrusted command envelope must contain **exactly** `type`, `company_id`, `appointment_id`, `key`, `payload`. Actor/principal/authorization claims in the payload or envelope are rejected.
- Company, current appointment, target task/delegation and active company state are checked against **canonical SQLite state** before executing existing Store/Workflows commands.
- A selected appointment belongs to the resolved agent; a different appointment for the **same** agent can be selected without combining privileges. Only the CEO role can create new root tasks through this gateway.
- Unknown actions (including deployments, policies, finance and credentials) are **default denied**, even if present in model text.
- Denied commands from attributed fixture sessions generate a minimal `command.denied` audit event containing **only action label and error code**, not arbitrary user/model payload. Unattributed unknown sessions are rejected without a tenant audit record.
- `Store.tx()` now supports nested SQLite savepoints. This allows gateway preflight + domain state + successful audit + receipt to belong to **one outer transaction**, without changing the existing Workflows command interface.
- Existing 46 tests remain; 25 new positive and negative gateway cases were added.

## Trust boundary and explicit limitations

```text
Untrusted command proposal (no authoritative identity fields)
        +
Opaque session issued by trusted in-process host fixture
        ↓
Gateway: host.resolve(session) + schema allowlist + company & appointment
        ↓
Store.tx() outer transaction: company state, role and existing command guards
        ↓
Store / Workflows nested savepoints + canonical writes + audit + receipt
```

**This is NOT cryptographic authentication.** `FixtureSessionHost.issue(company, agent)` is deliberately easy to use **only in trusted tests**. Anyone with direct Python access to that issuer, Store or SQLite connection can bypass the boundary. There is no HTTP server, credentials, OAuth, token TTL, principal attestation or OS process isolation. Never expose these APIs to a user, LLM, plugin, network client or tool subprocess as a trusted security boundary.

The real host must authenticate each caller and bind their real identity to the company and appointment. That adapter is **not implemented**.

### Allowlisted commands

`task.create`, `task.transition`, `task.start`, `task.resume`, `delegation.offer`, `delegation.accept`, `evidence.add`, `report.submit`, `report.begin_review`, `report.review`, `task.accept`, `report.sources`.

Company activation, `Actor` construction from an untrusted envelope, tenant-wide event listings, arbitrary database mutations, administrative policy writes and all real external effects are **not** exposed.

The real authorization engine (M2.3) — capability assessment, policy precedence, project ACL, budget limits, independent reviewers beyond the limited current check, owner approvals and external-action reconciliation — is **not implemented**. The existing fixture-only `AcceptTask` guards are insufficient for business acceptance.

### Session properties

- The test host keeps a weak, identity-based mapping between opaque Python session object and resolved principal. Copying an object or submitting a dictionary is not accepted.
- Test-host `revoke(session)` immediately prevents reuse of that particular session; it is **not** company-wide credential revocation.
- Appointment changes, unlike session revocation, are resolved from current SQLite data on every gateway command.
- A valid session for one agent cannot select another agent's appointment or tenant.
- Same-agent role switching still uses an explicit appointment selected per command, checked by Store. It does not union role privileges.

### Auditing

A successful command commits its entity transition/audit/receipt atomically through the nested transaction. A rejected attributed command rolls back changes and writes a separate minimal denial event. Tests check mutation absence and no secret payload leakage. Unknown sessions are not attributed to a tenant; a future trusted edge should log these independently with rate limits and safe correlation IDs.

## Local verification

```sh
python -m unittest discover -s tests -q
python -m compileall -q company_os tests
```

**Observed on 2026-11-08 in the isolated local environment: 71 tests passed (46 baseline + 25 gateway tests), zero failing.** The code was later uploaded to the proposed GitHub branch and compared to the local snapshots. **GitHub Actions/CI have not been run**.

Focused tests cover forged dictionary sessions, lookalike tokens, session revocation, alternate appointment spoofing, ended appointment, tenant mismatch, paused company, unknown action deny, unexpected `actor` fields, negative command side-effects, root task CEO restriction, forbidden direct assignment, manager-only delegation, stale revision, idempotency payload conflict, report read scope, independent review identity, safe denial audit, nested rollback, schema type restrictions and a permitted CEO→CTO report-review path.
