# M5.3-C — Trusted Host Authentication, One-Time Approvals, Budget and Lineage

**Status:** Design proposal — **not implemented**. This document does not attest that any C-stage mechanism exists.  
**Contract base:** M4.3 `ai-company-os.core@0.1.0-rc1`; M5.3-A/B1/B2 as merged (PRs #6/#7/#9).  
**Replaces today's fail-closed stubs:** `AUTH_APPROVAL_CONSUMPTION_NOT_IMPLEMENTED`, `BUDGET_RESERVATION_NOT_IMPLEMENTED`, `POLICY_REVIEW_LINEAGE_UNAVAILABLE`.

## Goal and non-goal

Enable the four guards that B2 deliberately fails closed, while keeping the repository a **local deterministic fixture**:

1. A trusted principal host that issues sessions only after verifying a **credential**, instead of any caller with `FixtureSessionHost.issue()`.
2. **One-time human approval consumption** bound to one command attempt (FIX-07: consumption binds to the attempt, not to success).
3. **Atomic budget reservation** for positive-cost commands.
4. **Verified contributor lineage** so independent review can be proven, not assumed.

This stage does **not** introduce OAuth/cloud IAM, network transport, multi-process locking, real LLM/tool execution, production secret storage, or company provisioning. An `OperationAttempt` ledger for external side effects remains out of scope until the runtime/tool adapter gate.

## Threat model delta (vs merged B2)

| Attack | B2 today | C target |
| --- | --- | --- |
| Anyone holding the process reference impersonates via `host.issue()` | Possible (test harness assumption) | Session issuance requires a verified principal credential; `issue()` without one raises |
| Approval replayed for a second command | Blocked by non-execution (fail closed) | Consumed atomically with the attempt; second use fails `AUTH_APPROVAL_ALREADY_CONSUMED` |
| Budget double-spend by parallel commands | Impossible (cost>0 denied) | Reserved inside the command transaction; rollback refunds automatically |
| "Independent" reviewer is a controlled subagent | Blocked by total non-execution of review commands | Blocked by append-only lineage records written from canonical data, never from model claims |

Unchanged: no untrusted caller may construct `Actor`, reach `Store`/`Workflows`, or write policy tables. All writes remain trusted-host operations.

## C1 — Principal attestation (replaces the fixture issuer)

```text
TrustedPrincipalHost
  - principal registry (host-side, provisioned out of band)
  - issue(principal_ref, credential) -> opaque session  |  AUTH_BAD_CREDENTIAL
  - resolve(session) -> Principal(company_id, agent_id)  # unchanged semantics
  - revoke(session)
```

- The registry maps a `principal_ref` to exactly one active appointment plus a **credential verifier** (secret comparison in constant time; credential supplied by the trusted transport layer, never read from command payloads or model text — M5.3-A12).
- Sessions remain non-serializable opaque objects; a session is bound to the host instance and dies with it (WeakKeyDictionary, as in B2).
- Honest limit: this is **fixture-grade attestation** (local registry + credential check), not production authentication. It removes "any code path can mint a session", which is the concrete forgeable step today.

## C2 — One-time approval consumption

`policy_approvals` already carries a `consumed` status and an exact-match index; B2 proves exact matching but never lets an approval enable a command. C adds:

- Column `consumed_by_receipt` (FK → `policy_gateway_receipts`, nullable, immutable once set — same trigger pattern as grant-version provenance).
- Policy context gains `approval_status` visibility so the evaluator can PERMIT on `status='approved'` only.
- The gateway consumes **inside the command transaction, before dispatch**:
  `UPDATE policy_approvals SET status='consumed', consumed_by_receipt=? WHERE id=? AND status='approved'`; zero rows updated ⇒ `AUTH_APPROVAL_ALREADY_CONSUMED`.
- Because consumption commits atomically with the command, a downstream domain failure **rolls the approval back to `approved`**. This is the FIX-07 interpretation: the approval was bound to one attempt and that attempt never committed; a retry must consume it again. A successfully committed command can never re-consume it (receipt exists ⇒ replay path, which skips re-consumption but still revalidates policy, grant, expiry and accountability).
- Approvals whose payload digest, target revision, policy version or resource no longer match remain `APPROVAL_REQUIRED` — the exact-match snapshot logic from B2 is reused unchanged.

## C3 — Atomic budget reservation

`policy_budgets` (company-keyed) already exists but is never written. C activates it:

- At enforce time, positive cost reserves first:
  `UPDATE policy_budgets SET remaining_units = remaining_units - ? WHERE company_id=? AND remaining_units >= ?`; zero rows updated ⇒ `BUDGET_EXCEEDED` (no read-then-write race; SQLite `BEGIN IMMEDIATE` already serializes writers).
- The reserved amount is recorded in the gateway receipt; **replay never re-reserves**.
- Rollback of the command transaction refunds automatically — reservation and mutation share one transaction, so no settlement logic is needed for internal commands.
- Budget exhaustion denies with `BUDGET_EXCEEDED`; a missing budget row for a positive-cost action denies with `BUDGET_NO_ROW`.

## C4 — Verified contributor lineage

- New append-only table `report_contributor_lineage` (company_id, report_id, version, contributor_agent_id, contribution_kind, attested_by_appointment_id, recorded_at) with `IMMUTABLE_*` triggers like receipts.
- Written **by the trusted host from canonical delegation/appointment records** at report submission — never parsed from report content or model output (M5.3-A12).
- The independent-review guard becomes: reviewer's agent identity must not appear in the lineage of the reviewed report **and** lineage must exist and be complete; otherwise `POLICY_REVIEW_LINEAGE_UNAVAILABLE` still applies (fail closed preserved for unattested history).

## Ordering and gates

| Step | Scope | Gate |
| --- | --- | --- |
| C-PR1 | C4 lineage + C3 budget (pure internal guards; no new authority) | All merged tests stay green; ~15 new negative tests |
| C-PR2 | C2 approval consumption + execution of approval-gated fixture commands | Exact-consume, rollback-restore and replay tests; approval still rejected without a human approver record |
| C-PR3 | C1 credential-verified principal host | Impersonation, revoked-credential and session-lifetime tests; legacy `FixtureSessionHost` quarantined to old test paths |

Each PR runs the full suite (`python -m unittest discover -s tests -q`, `python -m compileall`, `scripts/verify.py`) and raises the verifier's inventory floor monotonically.

**Still NO-GO after C:** external side effects, real LLM/tool calls, production authentication claims, multi-process deployment. C only unblocks *internal* command execution that B2 fails closed; the runtime/tool adapter remains a later gate.

## Open questions for review

1. **Credential model for C1:** local host-side registry (recommended) vs OS-level user mapping. The fixture has no transport layer, so the registry must be provisioned by test setup only.
2. **Approval rollback semantics:** restore-to-`approved` on transaction rollback (recommended; documented FIX-07 interpretation) vs burning the approval on any attempt.
3. **Budget accounting scope:** company-level (matches the existing `policy_budgets` key; recommended first) vs per-appointment budgets.
