# M4.4 — Minimal Vertical Slice & Implementation Readiness

**Status:** Proposal; no runtime implemented.  
**Contract baseline:** `ai-company-os.core@0.1.0-rc1` in `contracts/core-rc1.yaml`.  
**Scope:** One company, one root task, one hierarchical chain, durable evidence-backed reporting.

## 1. Objective

Prove the company OS can accept one owner request, safely delegate it through permanent agent identities, execute a bounded temporary subagent task, verify reports, and deliver an evidence-traceable CEO report **without losing state across restarts**.

This is an architecture-to-implementation bridge, not a change to the M1–M4.3 product scope.

## 2. Fixed fixture

- **Company:** `COMPANY-DEMO-001` (single tenant, software company as a *test fixture*, not a software-only platform).
- **Permanent agents / distinct appointments:** CEO → CTO → Engineering Manager → Backend Engineer.
- **Temporary worker:** Research Subagent, created only for a scoped research child task.
- **Human actor:** Owner, who submits the initial request and receives the final report.
- **Root task:** Investigate a harmless example API latency problem; results may use deterministic fixtures.
- **Forbidden external actions:** live deployments, payments, real customer data, privileged repository writes, uncontrolled outgoing messages.

Each agent has its own durable `AgentIdentity` and active `Appointment`. Runs are ephemeral. A temporary subagent must have a bounded lifetime, capabilities, delegation depth, and budget.

## 3. Non-goals for the first implementation

No multi-tenant production hosting, visual company builder, complete role catalog, real billing, enterprise SSO, unrestricted autonomous browsing or deployment, dynamic hiring, advanced semantic vector search, or heavy distributed infrastructure.

The first test uses a **deterministic runtime adapter**, not a model call. A real provider is integrated only after all deterministic workflow and authorization tests pass.

## 4. Single end-to-end workflow

| Phase | Responsible actor | Required durable effect |
| --- | --- | --- |
| 1. Request | Human Owner | Root Task created; CEO accountable |
| 2. Delegate | CEO | Authorized child Task + Delegation to CTO |
| 3. Delegate | CTO | Child Task + Delegation to Engineering Manager |
| 4. Delegate | Engineering Manager | Child Task + Delegation to Backend Engineer |
| 5. Research | Backend Engineer | Scoped temporary Research Subagent + research Task |
| 6. Report | Research Subagent | Immutable research report version + Evidence refs |
| 7. Review | Backend Engineer | Review decision; accept or request changes |
| 8. Deliver | Backend Engineer | Own implementation/analysis report + sources |
| 9. Review and roll up | Engineering Manager → CTO → CEO | Accepted reports with upward source references |
| 10. Return | CEO → Owner | Final executive report delivered with traceable evidence and honest unresolved status |

**Do not auto-close:** a parent Task is not accepted merely because child reports exist. A submitted report version is immutable; Review is the authoritative acceptance decision. Final CEO delivery and Owner approval are distinct when approval is required.

## 5. Minimum durable data

Use existing domain concepts only:

- `Company`, `OrganizationRevision`, `Position`, `AgentIdentity`, `Appointment`.
- `Task`, `Delegation`, `AgentRun`, `Report`, `Review`.
- `Evidence`, `MemoryRecord` (initially reference-based, without advanced search).
- `Policy`, `Approval` when a scenario requires it, `AuditEvent`.
- `OperationAttempt` as a safety contract; **no live external side effects** in this slice.

Every tenant-scoped record carries `company_id`; every agent command carries the agent identity, appointment, task context, and idempotency key. Mutable aggregates use `expected_revision` for concurrency checks.

## 6. Minimum ports (logical interfaces, not microservices)

1. **StateStore:** atomic persistence for entity state + audit event + durable event intent.
2. **CommandHandler:** schema, revision and transition guard validation.
3. **Authorizer:** deterministic policy/tenant/appointment/ownership checks, default deny.
4. **WorkCoordinator:** uses CommandHandler to create tasks, propose/accept delegations, and route reviews.
5. **RuntimeAdapter:** deterministic fixture first; later swappable model-backed execution.
6. **EvidenceStore:** content/revision references and integrity metadata, without accepting model assertions as verification.
7. **ReportTrace:** authorized traversal from CEO report to child reports and evidence.

Do not introduce separate network services merely to implement these interfaces.

## 7. Minimum commands and state guards

Initial commands: `CreateTask`, `AssignTask`, `StartTask`, `ProposeDelegation`, `AcceptDelegation`, `StartRun`, `SubmitReport`, `ReviewReport`, `SubmitTask`, `AcceptTask`, `CloseTask`, `PauseCompany`, `ResumeCompany`.

Existing M4.3 guard names stay canonical where defined; new names above are implementation planning candidates and **must be specified and reviewed before coding**. No new domain model is authorized by this list.

Critical guards:

- Company must be active to start new operational runs.
- Actor's active appointment, tenant and task scope must be valid at the execution boundary.
- Required child tasks must be accepted (or have an authorized waiver) before parent Task acceptance.
- A report's own author cannot satisfy an independent-review requirement via a second appointment.
- No Task enters `closed` before `accepted` and durable closure/audit records.
- Submit twice with same idempotency key + payload → same durable result; conflicting payload → reject.
- Authorization or schema rejection must not mutate canonical state.

## 8. Conformance gates

| Gate | Proof required | Release status now |
| --- | --- | --- |
| G1 Schema | Required fields, references, tenant boundaries, versions validated | Not run |
| G2 State | Valid and invalid transitions exercised | Not run |
| G3 Auth | Cross-tenant access, revoked appointments and self-review denied | Not run |
| G4 Invariants | 20 positive + 20 negative M4.3 cases implemented and passing | Not run |
| G5 End-to-end | FLOW-01 passes end-to-end; remaining flows tracked | Not run |
| G6 Recovery | Restart preserves state, idempotency works, interrupted run resumes safely | Not run |
| G7 Trace | Owner can trace final report to original evidence with authorization | Not run |

A test's existence is not evidence it passed. Record actual command, observed result and commit SHA for completed gates. **No production autonomous external execution** until all applicable safety gates have passed.

## 9. Implementation sequence: focused PRs

**PR-1: Data & state foundation**  
Define exact records, constraints, transaction semantics and executable schema validation. Seed the fixed company hierarchy. Test persistence after restart and negative tenant checks.

**PR-2: Deterministic workflow**  
Implement task/delegation/report/review commands and guards. Run the whole hierarchical fixture with the deterministic adapter. Test both accepted and changes-requested paths.

**PR-3: Governance, interruption & evidence trace**  
Verify authorization on every operation; concurrency conflicts; duplicate submissions; pause/resume; evidence lineage; safe checkpoints. No live external side effects.

**PR-4: Provider adapter (gated)**  
Choose a minimal runtime implementation by evidence, preserve deterministic test suite, add a single bounded model-backed research execution, and compare outputs with fixed acceptance criteria.

Do not begin PR-4 until deterministic workflow and authorization behavior is reproducible.

## 10. Decisions needed before PR-1

The implementation stack should be selected once, from explicit criteria:

- durable transaction support and schema constraints;
- low local setup/maintenance overhead;
- reproducible automated tests on developer machine and CI;
- simple tool/runtime integration;
- no cloud provider lock-in;
- language/framework choice should **not** alter the contract's meaning.

Do not add speculative infrastructure until a test demonstrates a need.

## 11. Definition of done for M4.4

M4.4 is planning-complete only when this document is reviewed against M4.3, the first slice boundary is accepted, the initial implementation stack is recorded as a decision, and PR-1 can start with unambiguous acceptance criteria.

**Current result:** scope specified; no source implementation, no passed gates, no model execution, no external actions.
