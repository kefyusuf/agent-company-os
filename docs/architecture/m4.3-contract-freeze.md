# AI Company OS — M4.3 Contract Freeze Candidate

**Contract:** `ai-company-os.core@0.1.0-rc1`  
**Status:** Review candidate; not implemented or tested.

## Scope
organization, work, knowledge, governance, company_composition, runtime

## Canonical decisions
| ID | Topic | Decision |
|---|---|---|
| FIX-01 | Report review | Submitted report version is immutable; Review is the authoritative acceptance decision. |
| FIX-02 | Assignment/accountability | ReassignTask and TransferAccountability are distinct authorized commands. |
| FIX-03 | Activation readiness | activation_ready is a validation result, not a Company state. |
| FIX-04 | Tenant-bound identity | AgentIdentity belongs to one company; runtime and model may be shared. |
| FIX-05 | Service requests | Cross-department ServiceRequest is linked to the requesting task and fulfilled through the target unit’s own task chain. |
| FIX-06 | Actor types | Agent, human and system_service are distinct authenticated actor kinds. |
| FIX-07 | Approval usage | Consumed approval binds to one operation attempt, not to success. |
| FIX-08 | Position occupancy | Reference model has at most one active primary appointment per Position. |
| FIX-09 | Knowledge verification | Accepted report does not automatically verify its claims. |
| FIX-10 | Unknown external result | Unknown operations require reconciliation before possible redispatch. |

## Canonical state names

- **task:** `draft`, `ready`, `assigned`, `in_progress`, `blocked`, `submitted`, `under_review`, `changes_requested`, `accepted`, `closed`, `failed`, `cancelled`
- **delegation:** `proposed`, `offered`, `accepted`, `fulfilled`, `rejected`, `declined`, `revoked`, `expired`, `terminated`
- **report_version:** `draft`, `submitted`
- **review_decision:** `accepted`, `changes_requested`, `rejected`
- **approval:** `draft`, `pending`, `approved`, `denied`, `cancelled`, `expired`, `consumed`, `revoked`
- **company:** `provisioning`, `provisioning_failed`, `inactive`, `active`, `paused`, `suspended`, `archived`
- **operation_attempt:** `planned`, `authorized`, `dispatched`, `succeeded`, `failed`, `unknown`, `reconciling`, `unresolved`

## Command guard catalog
| Command | Actor | Guards | Effect |
|---|---|---|---|
| `ProvisionCompany` | Owner or authorized company creator | Validated plan; approval bound to exact plan_hash; unique idempotency key | Creates Company+positions inactive; records audit |
| `AssignAppointment` | Authorized staffing manager | Company match; valid role and capabilities; one active primary occupant; no SoD conflict | Creates Appointment; records audit |
| `CreateTask` | Authorized requester | Single accountable owner; criteria; correct company; valid parent relation | Creates task in draft; records audit |
| `AssignTask` | Authorized task owner or manager | Task ready; valid assignee; capability and capacity; accepted assignment | Moves ready to assigned; records audit |
| `StartRun` | Assigned agent with active appointment | Company active; task assigned/in_progress; runtime and current authorization valid | Creates run lease; task starts when appropriate |
| `ProposeDelegation` | Assigned accountable or authorized manager | Scope, budget, depth and recipient eligible; no task cycle | Creates proposed delegation and linked child task per policy |
| `SubmitReport` | Authorized report author | Existing task and evidence references; submitted version immutable | Stores submitted report version and audit |
| `ReviewReport` | Authorized reviewer | Correct immutable report revision; independent if policy requires; evidence access | Stores independent Review decision; updates derived report view |
| `AcceptTask` | Authorized reviewer/accountable controller | Reports reviewed; criteria satisfied; mandatory children accepted/waived; approvals complete | Moves under_review to accepted with audit |
| `TransferAccountability` | Authorized current owner/manager | Valid receiving appointment; explicit acceptance; historical record preserved | Changes current accountability and records history |
| `ApproveAction` | Authorized approver | Explicit subject operation, resource, artifact digest, expiry and SoD | Stores immutable approval decision |
| `ExecuteExternalAction` | Authorized actor and approved attempt | Latest authorization; bound approval if required; idempotency/reconciliation guard | Creates one OperationAttempt; outcome tracked independently |
| `PauseCompany` | Owner or authorized operator | Company active; safe shutdown/recovery policy | Blocks new runs, checkpoints in-flight, preserves records |
| `PromoteMemory` | Authorized scope owner | Provenance, access, verification class and retention policy | Activates scoped memory with verification state, not assumed verified |

## Invariant conformance matrix
| Invariant | Positive case | Negative case |
|---|---|---|
| INV-001 | Switch model, preserve identity and history | Switching model replaces identity or history |
| INV-002 | Authorized command with all matching context passes | Command without active appointment changes state |
| INV-003 | CEO-rooted reporting tree validates | Manager A->B and B->A is accepted |
| INV-004 | One accountable appointment on task validates | Two simultaneous accountable owners accepted |
| INV-005 | Child assigned while parent retains owner | Parent owner silently cleared by delegation |
| INV-006 | Report accepted; task remains under_review until gates pass | Accepted report automatically closes task |
| INV-007 | All required children accepted or explicitly waived | Mandatory child in_progress yet parent accepted |
| INV-008 | Independent eligible reviewer accepted | Implementer reviews own work via another appointment |
| INV-009 | Read-only subagent delegated under write-capable parent | Subagent receives broader data or deploy authority |
| INV-010 | Approval matches operation, resource, revision, validity | Approval reused for different artifact or expired operation |
| INV-011 | Approved action has distinct succeeded/failed/unknown attempt | Approval status alone marks deployment succeeded |
| INV-012 | Old report retains former manager after revision | Manager change rewrites previous report recipient |
| INV-013 | Old identity and tasks remain after handoff | Ending appointment cascades deletion of prior reports |
| INV-014 | Memory links to report and evidence | Summary stored while source report silently discarded |
| INV-015 | Accepted research report keeps hypothesis unverified | All claims automatically marked verified upon acceptance |
| INV-016 | In-scope retrieval returns authorized project source | Cross-company or unauthorized customer source is returned |
| INV-017 | Unavailable capability causes task to wait | Unavailable frontend capability starts production work |
| INV-018 | Pause retains identity, tasks and history | Pause deletes records or starts a new operational run |
| INV-019 | Task state and audit event commit together | Task accepted with no durable audit event |
| INV-020 | Required deletion covers index and cache copies | Deleted sensitive source remains searchable in derived index |

## Go / No-Go
**Conditional GO:** Begin implementation of a narrow contract-validation vertical slice, keeping technology selection separate.

**NO-GO:** Autonomous execution against real external systems or production deployment prior to passing automated conformance gates.

### Required gates
- All 20 positive and negative tests implemented and pass
- Cross-domain scenarios implemented and pass
- State transition guards exhaustive and deterministic
- Permission-deny and tenant-isolation tests pass
- In-flight recovery and unknown external outcome tested
- Canonical data schemas machine-validated and versioned

### Known limitations
This is a normative design candidate, not a proven executable JSON Schema or implementation. Full field-level types, transition guard coverage, and data-retention procedures must be verified before production use.
